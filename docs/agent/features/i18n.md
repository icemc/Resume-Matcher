# Internationalization (i18n)

> **Multi-language UI, and multi-tenant (language-scoped) content.**

## Supported Languages

| Code | Language | Native Name | Flag | Message File |
|------|----------|-------------|------|--------------|
| `en` | English | English | 🇺🇸 | `messages/en.json` |
| `es` | Spanish | Español | 🇪🇸 | `messages/es.json` |
| `zh` | Chinese (Simplified) | 中文 | 🇨🇳 | `messages/zh.json` |
| `ja` | Japanese | 日本語 | 🇯🇵 | `messages/ja.json` |
| `pt` | Portuguese (Brazilian) | Português | 🇧🇷 | `messages/pt-BR.json` |
| `fr` | French | Français | 🇫🇷 | `messages/fr.json` |

> Source of truth: `apps/frontend/i18n/config.ts` (`locales`, `localeNames`, `localeFlags`) — must match backend `SUPPORTED_LANGUAGES` in `apps/backend/app/routers/config.py`. Note `pt` loads from `messages/pt-BR.json` (imported as `pt` in `apps/frontend/lib/i18n/messages.ts`).

## Two Independent Settings: UI Language vs. Tenant

This is not two client-side toggles anymore — they are architecturally different things:

1. **UI Language** — interface text (buttons, labels, navigation). One global, client-only setting shared across every tenant. Set in Settings, persisted to `localStorage` only.
2. **Tenant (content language)** — each supported language is its own **tenant**: its own URL segment (`/en/dashboard`, `/fr/dashboard`, ...), its own resumes/jobs/tracker data, its own AI-generated content. There is no independent "content language" picker anymore — the tenant *is* the content language. See [language-tenant-dashboards.md](../../plans/language-tenant-dashboards.md) for the full design.

## How It Works

- **UI translations**: plain JSON import, no external i18n library. `useTranslations()` (`apps/frontend/lib/i18n/translations.ts`) reads the current UI language from `LanguageProvider` and does dot-path lookup + `{placeholder}` substitution.
- **Tenant routing**: the `[locale]` App Router segment (`apps/frontend/app/[locale]/...`) determines the active tenant; `useTenant()` (`apps/frontend/lib/context/tenant-context.tsx`) derives it from `useParams()`, falling back to the default locale for an invalid/missing segment. `proxy.ts` (Next.js 16's renamed `middleware.ts`) redirects any locale-less path to `/${defaultLocale}${pathname}`.
- **API calls carry the tenant explicitly**: every list/create/upload backend endpoint takes a required `language` query param (GET) or body/form field (POST) — see [front-end-apis.md](../apis/front-end-apis.md). `lib/api/client.ts`'s `withTenant(endpoint, language)` appends it to query-string endpoints; POST bodies include `language` directly.
- **Content generation**: the backend resolves the LLM's `{output_language}` from the resume's own `language` column (i.e. the tenant it belongs to) — not from a separate config value.
- **Cross-tenant chrome**: `components/tenant/tenant-nav-bar.tsx` is shared chrome (mounted in `app/[locale]/(default)/layout.tsx`) showing which tenants are "configured" (have ≥1 resume, via `GET /resumes/configured-languages`) vs. not yet set up, and lets the user switch.
- **Internal navigation**: every internal `Link`/`router.push` call site uses `tenantPath(locale, path)` (`apps/frontend/lib/utils/tenant-paths.ts`) so the active tenant's URL prefix is never dropped.
- **Client-only draft/settings state** (resume builder draft, wizard draft) is scoped per tenant via `tenantStorageKey(tenant, baseKey)` (`apps/frontend/lib/utils/tenant-storage-key.ts`) so switching tenants never bleeds one tenant's unsaved draft into another's.

## Key Files

| File | Purpose |
|------|---------|
| `apps/frontend/messages/*.json` | UI translation files (`en`, `es`, `zh`, `ja`, `pt-BR`, `fr`) |
| `apps/frontend/lib/i18n/translations.ts` | `useTranslations` hook (UI language) |
| `apps/frontend/lib/context/language-context.tsx` | `LanguageProvider` — UI language only (`uiLanguage`, `setUiLanguage`) |
| `apps/frontend/lib/context/tenant-context.tsx` | `useTenant()` — active tenant, derived from the `[locale]` route param |
| `apps/frontend/lib/utils/tenant-paths.ts` | `tenantPath(locale, path)` — locale-prefixed internal navigation |
| `apps/frontend/lib/utils/tenant-storage-key.ts` | `tenantStorageKey(tenant, baseKey)` — per-tenant localStorage keys |
| `apps/frontend/proxy.ts` | Locale-prefix redirect (Next.js 16 Proxy, formerly Middleware) |
| `apps/frontend/app/[locale]/layout.tsx` | Validates the locale param, `generateStaticParams()` |
| `apps/backend/app/routers/_tenant.py` | `validate_tenant_language()` — 400s an unsupported tenant |
| `apps/backend/app/prompts/templates.py` | LLM prompts with `{output_language}` |

## Using Translations

```typescript
import { useTranslations } from '@/lib/i18n';

const { t } = useTranslations();
<button>{t('common.save')}</button>
```

## Using the Tenant

```typescript
import { useTenant } from '@/lib/context/tenant-context';

const tenant = useTenant(); // e.g. 'en', 'fr' — the active tenant/content language
```

## Storage

| Key | Scope | Purpose |
|-----|-------|---------|
| `resume_matcher_ui_language` | Global | UI language (localStorage only) |
| `${baseKey}_${tenant}` (e.g. `resume_builder_draft_fr`) | Per-tenant | Client-only drafts (resume builder, resume wizard) — via `tenantStorageKey()` |

`master_resume_id` is **retired** — the master resume is always derived live from the tenant-scoped resume list (`is_master` flag), never cached in localStorage.

## Adding a New Language

1. Create `apps/frontend/messages/{code}.json` with all translations (must structurally match `en.json` — see the i18n build-break constraint in `apps/frontend/CLAUDE.md`).
2. Add the locale to `apps/frontend/i18n/config.ts` (`locales`, `localeNames`, `localeFlags`).
3. Add `SUPPORTED_LANGUAGES` in `apps/backend/app/routers/config.py` (must match the frontend list exactly).
4. Add the language name to `apps/backend/app/prompts/templates.py`'s `LANGUAGE_NAMES`.
